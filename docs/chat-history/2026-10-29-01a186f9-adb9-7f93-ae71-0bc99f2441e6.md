# PRD: бронирование переговорной комнаты

## Цель и основа

Создать интерфейс бронирования одной переговорной на рабочий день **09:00–18:00**. Пользователь выбирает дату, видит занятость, создаёт, редактирует и удаляет брони.

Основа — локальный `bun-fsd-template`: React, TypeScript, Bun, FSD, Tailwind/shadcn, Zod, DI и MSW. Использовать существующую инфраструктуру шаблона. Ориентир реализации — **4–6 часов**.

## Пользовательский интерфейс

- Один экран: выбор даты, список броней по времени начала и форма создания/редактирования. Начальная дата — сегодня.
- Карточка брони содержит время, необязательное название и доступные действия.
- Форма: начало, окончание, необязательное название; при редактировании — сохранение и отмена. Дата определяется выбранным днём.
- Удаление требует подтверждения.
- Предусмотреть загрузку, пустой день, ошибку загрузки с повтором, отправку формы и ошибку операции. Повторная отправка во время запроса заблокирована.
- При смене даты форма сбрасывается, редактирование закрывается. Ответ предыдущего запроса не подменяет данные нового дня.
- На мобильном экране блоки располагаются вертикально. Поля имеют подписи, ошибки связаны с полями, действия доступны с клавиатуры, сообщения объявляются через `aria-live`.

## Правила и обработка ошибок

Одинаковые бизнес-правила проверяются в UI и mock API:

- `09:00 ≤ start < end ≤ 18:00`; длительность — от 30 до 120 минут включительно.
- Интервалы пересекаются, если `startA < endB && startB < endA`. Касание границ допустимо.
- При редактировании текущая бронь исключается из проверки пересечений.
- Создание доступно только для интервала, начало которого ещё не прошло. Время проверяется повторно при отправке.
- **Согласованное дополнение:** начавшиеся и прошедшие брони доступны только для просмотра; API также запрещает их изменение и удаление.

При `409` показать сообщение «Это время уже занято. Выберите другой интервал», повторно загрузить брони и **сохранить все поля формы**. Если обновление списка не удалось, сохранить форму и предложить повторить загрузку. Другие ошибки сохранения также не очищают введённые данные.

## API и архитектура

Сохранить предложенную модель `Booking` и HTTP-контракт:

| Метод | Назначение | Успешный ответ |
|---|---|---|
| `GET /api/bookings?date=YYYY-MM-DD` | Брони дня | `200`, `Booking[]` |
| `POST /api/bookings` | Создание | `201`, `Booking` |
| `PATCH /api/bookings/:id` | Изменение | `200`, `Booking` |
| `DELETE /api/bookings/:id` | Удаление | `204` |

Ошибки: `400` — нарушение правил, `404` — бронь отсутствует, `409` — пересечение. Формат ошибки: `{ code, message }`.

- Доменная модель, проверки интервалов и сервис бронирований — в `entities`; форма и действия — в `features`; композиция экрана — в `pages`.
- Расширить HTTP-клиент шаблона методами `PATCH`, `DELETE` и поддержкой ответа без тела.
- Запросы списка должны учитывать дату в ключе: существующий query-слой шаблона ключует запросы только по методу. Мутации выполнять вне механизма дедупликации запросов.
- MSW запускается до запросов приложения и работает в deployed demo. Хранилище — в памяти, сбрасывается при перезагрузке.
- Добавить воспроизводимый демонстрационный сценарий конкурентного бронирования: перед сохранением mock API занимает выбранный свободный интервал и возвращает `409`.

## Проверка и сдача

**Приёмочные сценарии:**

- Создание, редактирование и удаление отражаются в списке выбранного дня.
- Проверены границы рабочего дня, длительности 29/30/120/121 минута, обратный интервал, пересечения и касание.
- Редактирование без изменения времени успешно; самоконфликт отсутствует.
- Прошедшее время недоступно; переход времени начала во время заполнения формы учитывается при отправке.
- При `409` список обновляется, поля сохраняются; сетевые ошибки допускают повтор.
- Быстрая смена дат не показывает брони другого дня.

Проверки: unit-тесты правил и API, Playwright для CRUD и конфликта, `bun run check`, production build и проверка deployed demo.

**Допущения:** время локальное для браузера, точность — одна минута без обязательного шага 30 минут; одна комната, без авторизации, повторяющихся броней и постоянного хранения. При нехватке времени приоритет — правила, CRUD и восстановление после `409`; визуальная полировка откладывается.

| Состояние | Где хранить | Что содержит |
|---|---|---|
| Брони выбранного дня | `QueryStore` | Данные API, загрузка, ошибка запроса |
| Выбранная дата | Модель страницы | `selectedDate` |
| Форма | `useReducer` в `booking-editor` | Черновик, режим создания/редактирования, ошибки, статус сохранения |
| Удаление | Модель действия удаления | Выбранный id, подтверждение, статус запроса |
| Текущее время | Хук с внедряемыми часами | `now` для проверки доступности |

**Серверные данные.** Список броней хранится только в QueryStore, с ключом вида `bookings.list(date)`. После успешной мутации повторно загружаем день. Оптимистические изменения здесь добавят сложности: сервер может отклонить даже свободный по мнению UI интервал.

QueryStore шаблона потребуется доработать:

- Учитывать аргументы метода в ключе и передавать их через hook.
- Сделать `refetch` ожидаемым, чтобы различать результат записи и последующего обновления.
- Через query tracking проводить чтение. Мутации вызывать напрямую через сервис, сохраняя типизированную ошибку `409`.

**Форма.** В reducer предлагаю явно описать события: изменение поля, начало редактирования, отмена, отправка, успех, конфликт, ошибка и смена даты. Статус операции — объединение состояний, например `idle | submitting | conflict | failed`, вместо независимых флагов `isSaving`, `hasError`, `hasConflict`.

Черновик принадлежит форме. Обновление списка не должно его перезаписывать. При редактировании копируем исходные значения в черновик один раз; дальнейшие ответы API не меняют введённый текст.

**Производные значения.** Длительность, пересечения, доступность действий и возможность отправки вычисляем из черновика, броней и `now`. Отдельно хранить их в store не нужно — иначе появятся состояния, которые могут разойтись.

При серверном конфликте поток будет таким:

1. Сервис возвращает типизированную ошибку `409`.
2. Reducer переводит форму в `conflict`, сохраняя поля и id редактируемой брони.
3. Страница обновляет запрос текущего дня.
4. Новые брони участвуют в повторной валидации черновика.
5. Ошибка обновления отображается у списка; форма остаётся заполненной.

По FSD: **страница координирует дату и обновление списка**, feature управляет сценарием формы, entity содержит модель, правила и сервис, shared предоставляет транспорт и query-инфраструктуру. Связь страницы и feature — через props и callbacks.

Главное архитектурное решение здесь: **состояние запроса и состояние пользовательского ввода живут независимо**. Именно это обеспечивает сохранение формы при конфликте и ошибках загрузки.

```ts
  id: string;
  date: string;
  start: string;
  end: string;
  title?: string;
}

interface DaySlot {
  /** Минуты от начала рабочего дня: 0–539 */
  index: number;
  bookingId: string | null;
}

interface BookingDay {
  date: string;
  bookings: BookingDto[];
  slots: DaySlot[];
}
```

Например, бронь **10:00–11:00** займёт индексы `60–119`. Конечная граница исключается, поэтому следующая бронь с 11:00 займёт диапазон начиная со `120` и конфликта не будет.

Проверка выбранного интервала получается прямой:

```ts
function hasConflict(
  slots: DaySlot[],
  startIndex: number,
  endIndex: number,
  editingBookingId?: string,
): boolean {
  return slots.slice(startIndex, endIndex).some(
    (slot) =>
      slot.bookingId !== null &&
      slot.bookingId !== editingBookingId,
  );
}
```

Перед этой проверкой отдельно проверяем границы рабочего дня, порядок времени и длительность. Самоконфликт при редактировании исключается по `bookingId`.

Я бы зафиксировал такие правила архитектуры:

- **Брони — источник истины.** Слоты пересчитываются из них чистой функцией после загрузки дня.
- **Слоты не храним вторым изменяемым состоянием.** Иначе при создании, изменении и удалении придётся синхронизировать две структуры.
- **Прошедшее время проверяем отдельно.** Пустой слот может быть недоступен из-за времени; это не занятость другой бронью.
- **Черновик формы не занимает слоты.** Расписание меняется после подтверждения API.
- **После `409` загружаем брони и заново строим слоты**, сохраняя выделенный пользователем интервал.

Для проверки пересечений сами интервалы тоже просты: `start < otherEnd && otherStart < end`. Поэтому основная польза слотов здесь — единая модель для отображения свободного времени, выделения диапазона и его проверки. Для таймлайна или сетки я поддерживаю этот подход.

```ts
  /** Последняя подтверждённая версия. */
  confirmedSchedule: DaySchedule;

  /** Рабочая копия, которую отображает UI. */
  optimisticSchedule: DaySchedule;

  mutation: PendingMutation | null;
  error: MutationError | null;
}

type PendingMutation =
  | {
      type: "create";
      operationId: string;
      meeting: Meeting; // временный id
    }
  | {
      type: "update";
      operationId: string;
      meeting: Meeting;
    }
  | {
      type: "delete";
      operationId: string;
      meetingId: Meeting["id"];
    };
```

Обе версии — экземпляры одной доменной модели `DaySchedule`. Правила размещения и проекции слотов остаются внутри сущности, reducer только вызывает её операции.

Поток изменения:

1. Проверяем действие через `DaySchedule`.
2. Изменяем `optimisticSchedule` — пользователь сразу видит результат.
3. Отправляем запрос.
4. **Успех:** применяем ответ сервера, включая настоящий id созданной встречи, к подтверждённой версии; синхронизируем рабочую копию.
5. **Ошибка:** откатываем рабочую копию к подтверждённой версии. Черновик формы сохраняем.
6. **`409`:** после отката повторно загружаем расписание — подтверждённая версия могла устареть.

Машина объединит эти переходы и выполнение запросов, которые с `fromTransition` пришлось бы координировать отдельным контроллером.

При этом **guards управляют допустимостью переходов, а бизнес-правила остаются в `DaySchedule`**.

| Часть | Ответственность |
|---|---|
| `DaySchedule` | Рабочие часы, длительность, занятость слотов, проекция встреч |
| Guards | Разрешить или запретить операцию через методы сущностей |
| Actions | Сохранить черновик, применить оптимистическое изменение, подтвердить или откатить |
| Promise actors | Загрузить расписание, создать, изменить или удалить встречу |
| Состояния машины | Определить, какие действия сейчас допустимы |

В XState v5 guards должны быть **чистыми синхронными функциями**. Поэтому они не выполняют HTTP-запросы и не изменяют расписание. [Документация guards](https://stately.ai/docs/guards).

Предлагаю одну машину для экрана выбранного дня с такими состояниями:

```text
loading
├── успех → ready
└── ошибка → loadFailed

ready
├── невалидная операция → ready + ошибки проверки
└── допустимая операция → saving + оптимистическое изменение

saving
├── успех → refreshing + подтверждение изменения
├── 409 → refreshing + откат + сохранение черновика
└── другая ошибка → ready + откат + сообщение

refreshing
├── успех → ready
└── ошибка → refreshFailed

refreshFailed
└── повтор → refreshing
```

`loadFailed` и `refreshFailed` различаются: во втором случае уже есть локальное расписание, которое можно продолжать показывать.

Проверка перед изменением выполняется последовательно:

1. Валидность полей и принадлежность встречи выбранной дате.
2. Попадание в `workingTime`.
3. Допустимая длительность.
4. Доступность слотов — для создания или редактирования.
5. Ограничения прошлого времени.

Guard вызывает соответствующую доменную проверку. Если она не прошла, отдельная action сохраняет понятную причину ошибки — одного молчаливого запрета перехода недостаточно.

В `context` храним:

```ts
interface ScheduleContext {
  selectedDate: string;

  confirmedSchedule: DaySchedule | null;
  optimisticSchedule: DaySchedule | null;

  draft: MeetingDraft;
  pendingOperation: ScheduleOperation | null;

  validationErrors: ValidationErrors | null;
  operationError: OperationError | null;
}
```

`isSaving`, `isLoading` и похожие флаги отдельно не нужны: их определяет состояние машины. Обновления context выполняем неизменяемо через `assign`. [Документация actions](https://stately.ai/docs/actions).

Для API используем **`fromPromise` и `invoke`**, с результатами через `onDone` и `onError`. Вход операции фиксируется при переходе в `saving`, поэтому последующие изменения формы не меняют отправленный запрос. [Документация invoke](https://stately.ai/docs/invoke).

Дополнительно зафиксировал бы:

- Во время `saving` следующая мутация и смена даты недоступны.
- При `409` черновик сохраняется независимо от отката расписания.
- После успешной записи и неуспешного обновления повторяем **GET**, а не мутацию.
- Актуальный `now` передаём в событии отправки через внедряемые часы; guards не читают системное время самостоятельно.
- Сервер повторяет проверки: успешный guard не гарантирует отсутствие `409`.

**В этой архитектуре машина становится единственным владельцем локального расписания и жизненного цикла запросов.** QueryStore для бронирований тогда не нужен — иначе появятся два независимых владельца загрузки и подтверждённых данных. Jotai также пока не требуется.
