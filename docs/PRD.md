# PRD: бронирование переговорной комнаты

Обновлено: 2026-10-29. Основание: исходное задание и согласованные решения из [переписки](./chat-history/2026-10-29-01a186f9-adb9-7f93-ae71-0bc99f2441e6.md). Этот документ задаёт актуальные требования и имеет приоритет над ранними архитектурными решениями в [плане реализации](./booking-implementation-plan.md).

## 1. Цель и пользовательские сценарии

Пользователь должен видеть занятость одной переговорной на выбранную дату и управлять будущими встречами. Рабочий день — **09:00–18:00**. Инженерные приоритеты: бизнес-правила, предсказуемое состояние интерфейса и восстановление после серверного конфликта.

Один экран: выбор даты, список встреч по возрастанию начала и форма. Начальная дата — сегодня. На мобильном экране блоки расположены вертикально. Название встречи необязательно.

| ID | Требование |
| --- | --- |
| FR-001 | Выбирать дату; не выполнять запрос для пустого или невалидного значения |
| FR-002 | Просматривать встречи выбранной даты; при их отсутствии показывать пустое состояние |
| FR-003 | Создавать встречу с началом, окончанием и необязательным названием |
| FR-004 | Редактировать будущую встречу в отдельном редакторе; предзаполнять поля, поддерживать отмену |
| FR-005 | Удалять будущую встречу после подтверждения; отмена не изменяет расписание |
| FR-006 | Проверять рабочие часы, порядок времени и длительность |
| FR-007 | Запрещать пересечения, разрешать касание границ и исключать самоконфликт при изменении |
| FR-008 | Запрещать создание в прошлом; начавшиеся и прошедшие встречи оставлять только для просмотра |
| FR-009 | При 409 сообщать о конфликте, обновлять расписание и сохранять введённые данные |
| FR-010 | Показывать загрузку, пустое состояние, ошибку с повтором, выполнение и ошибку операции |
| FR-011 | При смене даты сбрасывать формы; не показывать запоздавший ответ другого дня |
| FR-012 | Предусмотреть воспроизводимую демонстрацию серверного конфликта |
| FR-013 | Оптимистически отражать создание, изменение и удаление; подтверждать результат или откатывать локальное изменение |

FR-001–011 и FR-013 обязательны. FR-012 — дополнительное удобство демонстрации; проверка обработки 409 обязательна независимо от наличия переключателя demo.

## 2. Правила времени и доступности

- Даты и часы локальные для браузера. Ввод времени — с точностью до минуты, без обязательного шага 30 минут.
- Начало и окончание находятся в пределах 09:00–18:00; `start < end`; длительность — **30–120 минут включительно**.
- Интервал полуоткрытый: `[start, end)`. Встречи 10:00–11:00 и 11:00–12:00 не конфликтуют.
- Начало новой встречи должно быть строго позже текущего момента. В момент начала существующая встреча уже доступна только для просмотра.
- Прошедшие даты доступны для просмотра. Создание, изменение и удаление начавшихся/прошедших встреч запрещены и в UI, и в mock API. При изменении проверяется также исходная встреча: её нельзя перенести из прошлого в будущее в обход запрета.
- Дата редактируемой встречи не меняется: она определяется выбранным днём.
- Текущее время передаётся в проверки явно; доступность обновляется при ходе времени, возврате фокуса и непосредственно перед отправкой. Сервер повторяет проверки перед записью.

Перед размещением сначала проверить формат и порядок границ, затем последовательно применить ограничения **workingTime → свободные слоты**. Отдельно проверить длительность и прошлое. Первая неуспешная проверка останавливает операцию и даёт понятную причину ошибки. Фильтры не изменяют и не перенумеровывают слоты.

## 3. Доменные сущности и данные

Два слайса: `entities/meeting` и `entities/day-schedule`. Между ними разрешён импорт через публичный API в направлении **day-schedule → meeting**. Встреча не зависит от расписания. Доменные сущности не зависят от React или XState.

**Meeting** содержит id, дату, начало, окончание и необязательное название. В доменной модели время выражается целым номером минуты суток; API использует строки `HH:mm`. Преобразование выполняется на границе API.

**DaySchedule** управляет встречами дня и их проекцией на слоты:

| Поле DayScheduleData | Значение |
| --- | --- |
| `date` | Дата дня, `YYYY-MM-DD` |
| `workingTime` | Начало включительно и окончание исключительно, в минутах суток: 540 и 1080 |
| `minSlotMinutes` | Минимальная длительность бронирования: 30 |
| `maxSlotMinutes` | Максимальная длительность бронирования: 120 |
| `meetingsById` | Полные данные встреч по id; в доменной модели — ReadonlyMap |
| `slots` | Readonly-массив из 1440 элементов; индекс — номер минуты суток, значение — id встречи или null |

Размер ячейки всегда равен одной минуте; `minSlotMinutes` и `maxSlotMinutes` ограничивают длительность встречи. Например, 10:00–11:00 занимает индексы 600–659; индекс 660 уже не принадлежит этой встрече.

Расписание должно уметь:

- Собираться из набора встреч выбранной даты и возвращать встречи, отсортированные по началу, без потери id и названия.
- Проецировать добавление, изменение и удаление встречи на слоты.
- Отдельным методом проверять попадание встречи в `workingTime`.
- Отдельными boolean-методами проверять свободные слоты при создании и изменении. При изменении собственные слоты распознаются по id самой встречи.
- Возвращать новую согласованную версию либо доменную ошибку. Некорректный набор встреч не должен молча перезаписывать занятые слоты.

`availableTime` не хранится: это динамическая проверка занятости. Поле `excludeMeetingId` не требуется. `null` означает отсутствие встречи, но не разрешение бронирования вне рабочих часов или в прошлом. Каталог и слоты изменяются только через операции DaySchedule; отдельные компоненты не редактируют их независимо.

Статусы «предстоящая / идёт / завершена» вычисляются из встречи и текущего времени, отдельно не сохраняются.

## 4. Состояние приложения и XState v5

Использовать **полноценные машины XState v5**, а не fromTransition. Основа приложения — React, TypeScript и Bun из `bun-fsd-template`, с FSD, DI, Zod и существующими UI-компонентами. Jotai и отдельный дублирующий store бронирований не вводить.

| Владелец | Ответственность |
| --- | --- |
| `dayScheduleMachine` | Выбранная дата, подтверждённое и оптимистическое расписания, загрузка и обновление, создание/удаление, API-операции, commit/rollback |
| `meetingEditorMachine` | Исходная редактируемая встреча, черновик, ошибки полей и сохранения, отправка и отмена |
| DaySchedule / Meeting | Данные и бизнес-правила; guards используют эти правила |

QueryStore шаблона не является вторым владельцем бронирований. Машина расписания располагается в модели страницы, редактор — в feature. React отображает snapshots и отправляет события.

Редактор вызывается как дочерний актор на корневом уровне машины расписания и сохраняет экземпляр при сохранении и обновлении списка. Изменение расписания и часов передаётся событиями; обновление снимка не перезаписывает черновик. В родителе хранится только id открытого редактора и зафиксированный payload запроса, а не вторая редактируемая форма.

Состояния расписания: загрузка, ошибка загрузки, готовность, сохранение, обновление после записи/конфликта, ошибка обновления. При готовности различаются создание, открытый редактор и подтверждение удаления. Состояния редактора: закрыт, редактирование, отправка, конфликт, ошибка сохранения. Флаги вроде `isSaving` не дублируют состояния машины.

Guards и actions извлекаются в именованные чистые функции для прямого тестирования: проверки возвращают boolean, преобразования — изменения контекста, конструкторы сообщений — объекты событий. Отправка сообщений, HTTP и другие эффекты остаются в адаптерах XState. В приложении API вызывается через invoke/fromPromise; guards синхронны и не выполняют запросы.

События имеют строковый `type`. Соглашение проекта — строчные слова через точки, например `meeting.save.requested`, `editor.save.requested`, `schedule.mutation.succeeded`. У отмены редактирования и удаления разные события. Полный протокол описан в [документе симуляции](./day-schedule-simulation.md).

## 5. Оптимистические операции и восстановление

1. Проверить операцию; для редактора машина расписания повторно проверяет запрос по актуальным данным.
2. Сохранить подтверждённый снимок и сразу изменить оптимистическую версию, отображаемую UI. При создании использовать временный id.
3. Выполнить запрос. Разрешена одна мутация за раз; во время сохранения и последующего обновления дня смена даты и новые мутации недоступны.
4. При успехе применить данные сервера, заменить временный id настоящим, подтвердить локальную версию и обновить день. Редактор после успешного сохранения закрывается.
5. При ошибке откатить оптимистическое изменение; черновик сохраняется, повтор становится доступен.
6. При 409 показать сообщение о занятом времени, откатить изменение и повторно загрузить день. Редактор остаётся открытым с теми же полями; обновлённые слоты участвуют в следующей проверке.

Если GET после 409 завершился ошибкой, сохранить черновик и дать повтор загрузки. Если GET не удался после успешной записи, сообщить «Встреча сохранена, не удалось обновить расписание», оставить подтверждённую встречу и повторять только GET, без повторной записи.

Фоновый/запоздавший ответ не перезаписывает незавершённое оптимистическое изменение или данные другой даты. При разрешённой смене даты закрываются редактор и формы предыдущего дня.

## 6. API, интерфейс и критерии приёмки

Реальный сервер не нужен. Mock HTTP API на MSW валидирует те же бизнес-правила, умеет возвращать 409 и работает в production demo. Хранилище — в памяти одной вкладки, со сбросом при перезагрузке. Запуск worker предшествует запросам приложения; его файл должен раздаваться в dev и deployed demo.

Booking DTO сохраняет контракт задания: `id`, `date: YYYY-MM-DD`, `start/end: HH:mm`, необязательный `title`. Данные API валидируются через Zod; сетевой слой и маппинг отделены от UI и заменяемы через DI.

| Запрос | Успех | Ошибки |
| --- | --- | --- |
| GET /api/bookings?date=YYYY-MM-DD | 200, Booking[] | 400 для невалидной даты |
| POST /api/bookings | 201, Booking | 400, 409 |
| PATCH /api/bookings/:id | 200, Booking | 400, 404, 409 |
| DELETE /api/bookings/:id | 204 без тела | 400, 404 |

Ошибка содержит `code` и `message`; клиент сохраняет HTTP status. Невалидные данные и запрещённые изменения прошлого — 400, отсутствующая встреча — 404, пересечение — 409. Удаление с 204 не должно пытаться разобрать JSON.

Критерии приёмки:

- CRUD отражается оптимистически, затем подтверждается либо откатывается; отмена редактирования/удаления не изменяет встречи.
- Проверены границы рабочего дня, start < end, длительности 29/30/120/121 минута, минутная точность, касание, вложение и пересечение интервалов.
- Собственная встреча не конфликтует с собой; чужая блокирует изменение. Каталог и 1440 слотов согласованы после каждой операции.
- Прошедшие и начавшиеся встречи доступны только для просмотра. Наступление начала во время заполнения или подтверждения учитывается повторной проверкой.
- При 409 введённые поля и экземпляр редактора сохраняются; после обновления видна конкурентная встреча. Ошибка повторного GET допускает отдельный повтор загрузки.
- Успешная запись с неуспешным обновлением не провоцирует повтор мутации. Двойное нажатие не создаёт вторую операцию.
- Быстрая смена дат не смешивает ответы. Ни загрузка списка, ни ошибка обновления не очищают редактор текущей даты.
- Загрузка, пустой день, ошибки и выполнение операции имеют различимые состояния. На ширинах 360 и 1280 px нет горизонтальной прокрутки; поля подписаны, ошибки связаны с ними, CRUD доступен с клавиатуры, сообщения объявляются через aria-live, фокус после закрытия возвращается на доступный элемент.
- Чистые правила и преобразования проверены отдельно; взаимодействие машин — runtime-тестами; пользовательские сценарии — Playwright. Выполнены check, build, E2E и CT, отдельно проверен опубликованный demo.

Авторизация, БД, интеграции, повторяющиеся встречи, несколько комнат и синхронизация вкладок не входят в объём.
